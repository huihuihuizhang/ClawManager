## 2. 分阶段开发与完成判据

每阶段有独立 feature gate、migration 边界、测试安装的启用/回滚办法和验收报告。后一阶段不能补交前一阶段的合同或安全门禁；产品 P0 GA 仍须五阶段全部通过（第 16～18 节）。

### P0-0a：合同与能力冻结

1. 建立 schema object registry：扫描 embedded migration 中的对象，向各 owner 收集归属/策略/verifier，补齐 D 的 `resources` 与 `system_backup`；以静态扫描和 `information_schema` 检查覆盖率（第 5 节）。
2. 组织 capability spike，把部署形态、CSI/HostPath、KMS/secret、Redis、对象存储、只读 preflight 和外部 catalog 的能力要求变成可运行证明、fixture 与缺口清单（第 2、7～12、17.1 节）。
3. 落盘第 3 节的 OpenAPI、JSON Schema、enums、接口与 registry 冻结包；所有文件标相同合同版本，签名、provider 动作、资源/evidence、监控等合同不能留待后续阶段补做。
4. 从合同生成或以 snapshot/parity test 锁定 Go/TypeScript DTO；建立 closed-schema/redacted fixture、主计划与两份派生文档的版本门禁；依第 3 节把主计划待替换的手写闭集改为机器合同生成的只读快照。
5. 请 A/B/C 用各自 fixture 和权限负测签收接口，公共合同至少由一名非实现 owner 交叉评审。接口缺口回到合同修订，不用 D 私有字段填缝。

**完成判据**：完整合同包、registry、capability 证据、parity/负测和交叉评审进入仓库；版本一致且第 3、17.1 节门禁通过。未通过前只做 fixture、migration 草案和接口骨架。

### P0-0b：安全基础与可接管控制面

1. 用追加 migration 建系统备份控制表、约束和索引，覆盖合同中的任务/operation、claim/gate/lease、资源 inventory、external action、evidence/log、dependency/capability、catalog scan/record、nonce、GC/tombstone、promotion 等实体；将 D 的资源域 ensure-only 建表移入 migration。跨 owner 的 risk/chat DDL 由对应 owner 提交或共同评审（第 5～6、17.1 节）。
2. 验证 schema coverage、migration catalog/schema hash、控制表 dump 排除、migration runner 与 gate 的互斥；repository 不再在构造时创建业务表，四套部署的 MySQL init 与 embedded migration 保持同源（第 5、17.1 节）。
3. 建独立 `system-backup-controller` 进程/Deployment、ServiceAccount、leader lease 与 DB claim。先用无 provider 副作用的 fake runner 验证 CAS、数据库时间、失去 leader/claim 后接管，再接入 D 的 gate/fencing 与 B 的 participant/runner/relay（第 6～8、17.2 节）。
4. 从全部官方部署移除 app `cluster-admin`，补齐 app 现有 runtime/sync 最小权限；为 controller/Job 分离 RBAC、NetworkPolicy、准入限制、资源限额及身份。与 A/B/C 联合验证 Secret/KMS/artifact/catalog 权限；正向动作和负向 SubjectAccessReview 均通过（第 7.1、17.1、18 节）。
5. 接入部署/数据库 feature gate、首次启用持久化、controller liveness/readiness；把 A 的 audit/redaction、request ID、strong-auth/nonce 接入管理 mutation 公共入口。准备 D 的 resources 数据模块骨架与 redacted fixture（第 6、10、14～15 节）。

**完成判据**：migration/coverage 可重复验证、运行时 DDL 消除、官方部署权限隔离正负测通过、controller 在测试安装中安全 claim/接管且 gate/fence 不变量成立，feature gate 可独立回滚。未过门禁不创建真实备份 Job（第 5～8、17.1～17.2、18 节）。

### P0a：备份链路与 resources 域

1. 在冻结 DTO 上实现备份 Admin 创建/查询/取消、任务/operation 持久化、幂等、权限和审计；handler 只鉴权、校验、写控制库，controller 负责状态推进、deadline、取消竞争、事件/检查结果与终态投影（第 4、6、14 节）。
2. 编排 B 的 capture/checkpoint/staging/relay、A 的 Secret/KEK/签名/evidence、C 的 artifact/finalizer/external-action/catalog；只消费冻结结果，不复制 runner、provider 或签名实现（第 7～11、16 节）。
3. 实现 D 的 `resources` collector 与 backup verifier：按 registry 处理系统镜像、出站例外、安全扫描、北向平台管理配置及其审计、通用审计的范围、统计、redaction、快照边界和跨域引用；北向配置的认证与实例字段分别请 A/B 交叉评审；deployment resources/Secret bundle 按各自 owner 接入，不能让通用 resources collector 获取业务 Secret（第 5、7.4、10～11 节）。
4. 做接管和 finalization 故障注入：验证不可逆动作前的持久化意图、响应丢失后的权威判等、cancel/commit 竞争、凭据/资源清理和历史资格投影（第 4、7～9、17.2 节）。

**交接输入**：B 的 runner/relay/checkpoint、A 的安全/evidence、C 的 artifact/external-action/catalog fixture、合同版本和权限负测。**完成判据**：固定测试集完成备份闭环，六个必选 part、六类业务及控制面检查可验；D 的 resources 结果可单独验证；执行与资格结论分开，Console 不是本阶段前置（第 10、16～18 节）。

### P0b：灾备发现、隔离演练与生产只读 preflight

1. 将 C 的 catalog scan/import、artifact read/full verify 与 B 的隔离资源、normalizer、cleanup 接入 controller 编排；A 提供只读证据与安全验证。可先用固定 committed artifact fixture 开发只读 adapter/verifier，真实集成等待 P0a 产物（第 12、14、16 节）。
2. 完成 D 的 `resources` restore/preflight verifier 和 normalization registry 项；控制面 verifier 验证源控制表行未进入恢复目标、control-evidence 只读且 redacted（第 5、10、12.1 节）。
3. 实现生产目标只读 preflight/diff 的创建、取消、查询和报告失效判定；测试 planned/observed 两道隔离门、只读权限和预算。P0 不接生产 restore execute（第 12.1、12.3、14、17.3 节）。
4. 完成 `/admin/backups` 的 overview、配置、备份详情/事件/日志、manifest、catalog、drill/cleanup、preflight/diff 页面；只消费冻结 DTO，按第 14.3 节呈现不同结论和轮询。

**交接输入**：C 的 catalog/import/reader、B 的 isolation/normalizer/cleanup、A 的 evidence/strong-auth、P0a 的 committed artifact。**完成判据**：新灾备安装不依赖源控制库即可发现、导入、full verify、隔离演练；生产 preflight 只读、报告漂移可判失效；resources 与控制面 verifier 可验（第 12、14、17.2～17.3、18 节）。

### P0c：retention、promotion、监控和发布证据

1. 接入 C 的 prune provider/artifact health、B 的 orphan/resource 收敛、A 的审计/安全告警；D 实现 dry-run、confirmation、execute/retry 的 Admin 编排、权限/幂等/operation 和 Console 流程。对象结果与 catalog 后置动作仍以各自权威记录为准（第 13～14、16 节）。
2. 实现 promotion 创建/撤销、活动 baseline 的健康/hold 投影和安装级 readiness 汇总；按冻结判定表测试 backup、drill、cleanup、artifact、catalog 变化（第 4.3、13～15、17.1 节）。
3. 持久化并汇总 dependency-health、provider capability、catalog scan-state、source-writer check、alert state 等监控新鲜度；对接各 owner 采集器，完成 metrics registry、告警、controller 自监控和 overview，具体 type/label/阈值只取机器合同（第 6.2、15、17.1 节）。
4. 协调 control metadata GC、A 的 evidence GC、C 的 catalog/health、B 的资源 GC 做引用和接管测试；不能靠 Console 绕过 ownership 不明或证据未清理的状态（第 12～13、17.2～17.3 节）。
5. 汇总四种真实部署矩阵的固定数据集、故障注入、权限负测、灾后隔离演练和 redacted release evidence；逐项记录资源、命令、结果与清理证明，对照第 18 节做 P0 发布评估（第 17.4～17.5 节）。

**完成判据**：prune 的保底/hold/lease/重试与 catalog 后置结果可追踪；promotion 和监控区分历史资格与当前可用性；四矩阵各自证据通过并汇总；无测试产物残留（第 13～18 节）。

## 3. 交接与首批可审查提交

| 对方 | D 提供 | D 接收时检查 |
| --- | --- | --- |
| A | 冻结的安全/审计/evidence 合同引用和控制面接入点 | Secret/KEK/签名、strong-auth、audit/redaction、evidence fixture、权限负测与异常映射 |
| B | 冻结的 runner/relay/gate、staging/restore resource 调用点 | Job-set/checkpoint、participant、relay、隔离资源、normalizer/cleanup fixture、接管与权限证据 |
| C | 冻结的 artifact/external-action/catalog、health/prune 调用点 | provider capability、finalizer、catalog scan/import、artifact verify/prune fixture、幂等/冲突/权限负测 |

每份交付按“合同版本 → schema/fixture → 权限证明 → 故障接管测试 → owner 签收”检查。未通过则回 P0-0a 修公共合同或退回对应 owner 修实现；未分配工作不默认归 D（第 16 节）。

建议先交付：① P0-0a 盘点/capability 证据；② 完整机器合同与 parity（通过后才称冻结）；③ P0-0b migration/registry/DDL 迁移；④ P0-0b 权限隔离与 controller 骨架。随后按 P0a、P0b、P0c 分别提交可验收集成，避免把 Console、promotion 或四矩阵捆成前一阶段的不可验证大分支。

只使用仓库已有依赖，不自行安装。测试/构建开始前记录已有产物和资源，结束后只清理本次 run 创建且有所有权标记的内容；具体清理口径完全引用主计划第 17.5 节。
