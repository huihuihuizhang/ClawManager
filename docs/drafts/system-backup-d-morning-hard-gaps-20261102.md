# 明早同版本部署硬缺项草稿

供 root 审核，目标为 2026 年 11 月 3 日真实页面一次完整非空六域备份发布、独立读回、catalog 可见和同任务成功，不做隔离还原。这个目标不自动要求 task_purpose=acceptance 或灾难恢复资格，也不授权改为 functional_test 或部分备份。当前工作树仍有首次安装、配置激活和六域准入的代码缺口。下面区分通用门槛、acceptance/DR 额外条件、尚未建立的现场材料和未完成的验收；“现场待证”不表示已实时确认远端材料不存在。现场事实仅引用仓库现有回执，未重新连接现场。

责任方采用现有分工：A 为安全和原始权威，B 为执行及原窗口性能，C 为发布和独立读回，D 为生产接线和部署，现场 owner 为有权提供原始材料及操作现场的人。条目按依赖顺序排列，不表示每项都会同时成为第一处错误。

## 24 个资源 owner 的准确集合

这是**已有 main 三个 registry 加上三个材料 validator 之后**的剩余集合；不是当前 main 只缺 24 的意思。

- 6 个 registry：`parts`、`redis_sources`、`failure_domains`、`disaster_identity_mapping`、`source_writers`、`secret_allowlist`。
- 17 个 reference：`artifact_write`、`artifact_read`、`artifact_delete`、`artifact_upload_issuer`、`evidence_store`、`evidence_write`、`evidence_read`、`evidence_delete`、`evidence_kek`、`kek`、`capture_signing`、`acceptance_signing`、`catalog_signing`、`catalog_read`、`catalog_append`、`catalog_snapshot`、`status_relay`。
- 1 个跨资源验证：`cross_resources`。

已有三个 main registry 是 `rbac_bindings`、`provider_proof_issuers`、`strong_auth_issuers`。三个已实现但未进入真实 main 的材料 validator 是 `nonce_hmac`、`artifact_ca`、`evidence_ca`。它们的 binding 仍需真实原始权威，不能由测试 DTO 推导。

## 已更正和保留的边界

quiesce 旧 Pod 重检缺陷已有 root 组件验证，R3 真实 SQL 运行也已越过该阻塞，因此不再把它列为当前第一失败点。publish staging caller 已接线。Vault JWT 和持久化重启已有现场回执，因此不再列为“Vault 尚未安装”。这些完成项均不消除表中的后续门槛。

页面默认 acceptance 是当前实现事实，不是本次用户目标的定义。`frontend/src/types/systemBackupContract.ts` 当前 purpose 闭集仅 acceptance/functional_test；`production_source_profile.go:93` 的六域 capture 扩展也只接受 acceptance。因此不能凭空改请求为 ordinary/backup 字符串，也不能改成 functional_test。普通完整备份需要 C/D 在现有合同上明确成功、产物可用和 DR 不合格能够并存的语义，再做最小接线；本次只读清单没有改这些生产规则。C 尚需对普通 not_provided 发布收尾给出明确交叉结论，代码检查不替代其签收。
